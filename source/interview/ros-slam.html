01 · 三张图究竟怎样对应？

从世界点到像素：相机移动后，同一个岸边三维点会落在新的像素位置。针孔投影可写为 p ∼ K · Tcw · P；K 是内参，Tcw 把地图中的点变换到相机坐标。示意图采用无畸变相机，实机必须使用标定模型。

“图像变换”不只是把图片平移或旋转：第 2 图同时展示灰度化与跨帧对应。真实 ORB-SLAM3 提取 ORB 特征、建立匹配并进行几何验证，利用静态场景与运动视差估计位姿和三维点。一般三维场景的各点深度不同，不能用一个二维仿射变换解释全部像素运动。

地图需要运动基线：第 3 图在地标被连续观察且像素位移足够后显示它。这里用已知场景坐标演示“逐步建图”，没有进行真实三角化。纯旋转或远处几乎没有视差时，真实系统的深度估计会退化。

单目的边界：纯单目视觉不能凭图像恢复绝对米制尺度。稀疏特征地图也不等于可供避障的占据地图。若需要真实距离，可另行设计 GNSS、已知尺度或视觉惯性方案；这些均不假定船上已具备。

02 · ROS 2 节点、话题与时间戳怎么接？

以下是建议接口，不是 ORB-SLAM3 自带的话题。官方仓库提供核心库与 ROS 示例，不能当成开箱即用的 ROS 2 Jazzy 包。需要自行实现或审查一个 ROS 2 wrapper，并固定源码版本与依赖。

生产者 → 消费者建议话题 / 类型必须约定的含义
云端解码 → SLAM wrapper/boat/camera/image_raw
sensor_msgs/msg/Image		保留曝光采集时刻；frame_id=camera_optical_frame，明确 mono8 / rgb8 / bgr8。
标定发布 → wrapper/boat/camera/camera_info
sensor_msgs/msg/CameraInfo		与图像分辨率、裁剪、畸变模型一致；wrapper 明确将标定转为 ORB-SLAM3 配置。
wrapper → 可视化/slam/pose · geometry_msgs/msg/PoseStamped
/slam/path · nav_msgs/msg/Path		仅在跟踪有效时输出有效位姿；保留对应图像采集时间与地图会话标识。
wrapper → RViz2/slam/points
sensor_msgs/msg/PointCloud2		稀疏地标快照；同步访问地图，不能直接跨线程遍历变化中的内部对象。
wrapper → 监控 / 回传/slam/status
diagnostic_msgs/msg/DiagnosticArray		跟踪状态、帧龄、丢帧数、map_id；失跟踪不伪装成零位姿。

ROS Image 的 header.stamp 表示图像采集时刻，不能用云端收到数据的时间代替。传输层需保留 session_id、frame_id、capture_timestamp、calibration_id；如果编码器重排帧，使用展示时间与元数据恢复采集顺序，再串行调用 TrackMonocular(image, timestamp_seconds)。

同一会话内传入时间必须递增；时钟重置时新建会话并重建时间基准。船云时钟需要同步或估计偏差才能测量端到端帧龄。图像话题可从 SensorDataQoS 的小队列、best effort 起步，发布者和订阅者必须兼容；标定也必须保证 wrapper 已收到后才处理图像。

03 · Tcw、光学坐标系与船体坐标系

约定 T_ab 将 b 系坐标变换到 a 系。ORB-SLAM3 的 Tcw 是世界到相机的变换；发布相机在地图中的位姿时使用 Twc = inverse(Tcw)。还必须检查跟踪状态，不能只凭返回对象存在就认为结果有效。

ROS 光学坐标约定为 x 向右、y 向下、z 向前；船体 base_link 通常为 x 向前、y 向左、z 向上。不要直接把光学坐标的平移和旋转贴上 base_link 标签。

T_map_base = T_map_camera × inverse(T_base_camera)

T_base_camera 来自相机到船体的外参标定。上述组合要求平移的尺度一致：纯单目地图没有米制尺度时，不能直接混合以米计的相机安装偏移。教学可先在独立的 slam_world 下显示相机轨迹，并明确任意单位；获得尺度与方向对齐后再接入船体 TF。

纯单目地图的初始方向也不保证符合 ENU 或重力方向。回环或切换地图可能让全局位姿跳变；需要连续控制时应另有本地 odom 估计，再设计 map → odom → base_link。不能把会跳变的云端全局位姿直接当连续里程计。

04 · 无人船场景与云端部署的关键取舍
  • 看岸边：尽量让建筑、码头、岸边固定物占据有效视野。波纹、反光、天空和移动船只不适合当稳定地标；可评估水面区域掩膜，但这需要额外实现与验证。
  • 先清晰，再提帧率：优先稳定安装和短曝光，避免运动模糊；全局快门可减少滚动畸变。可从 1280×720、20 Hz 进行试验，最终按相机、上行带宽和云端耗时调整；这是配置起点，不是性能保证。
  • 编码取舍：低延迟视频编码可降低带宽，但压缩损伤、长 GOP 和丢包可能破坏特征。关闭 B 帧、合理设置关键帧间隔作为试验起点；若分辨率或裁剪改变，内参必须对应更新。
  • 有界处理：云端待处理图像队列可从 2–3 帧起步，过期帧及时丢弃；跳帧过大又会导致失跟踪，因此还要联合调整采集率、码率和算力。断线恢复时等待可解码帧，标记新会话或执行重定位。
  • 控制留在船端：回传结果附带采集时间和有效状态。过期、失跟踪或新地图尚未对齐的位姿不能驱动当前控制；本地控制、急停与失联策略应独立于云链路。
  • 服务器单独部署：本 Netlify 页面承载学习笔记与动画。持续运行 ORB-SLAM3 需要另配云主机或容器服务；先以 CPU 跟踪 / 建图压测，按实测资源需求扩容。
05 · 从离线回放到实船，如何验收？
  1. 标定与离线：保存标定参数、分辨率和图像采集时间。先用岸边录像离线回放，检查初始化、跟踪状态和相同地点的重定位；不要先把网络问题混进算法问题。
  2. ROS 2 接口：核对话题类型、QoS、图像编码、时间戳递增、坐标轴方向和位姿求逆。RViz2 中相机移动方向应与原始录像一致。
  3. 真实链路：记录采集、解码、开始跟踪、结束跟踪和回传时间；统计队列长度、丢帧与帧龄的 P50 / P95。阈值由船速、任务和控制要求决定。
  4. 故障注入：测试限速、乱序、断网、重连、相机重启和时间戳回跳。检查不会无限积压，也不会持续发布失效位姿；必要时清空会话并明确重建地图。
  5. 量化评估：若有 GNSS / RTK 等真值，纯单目轨迹需说明 Sim(3) 对齐及尺度处理，再报告 ATE / RPE 与跟踪成功率。没有真值时只报告可观测状态，不能把“轨迹看着平滑”当作精度验证。

补充 1 · 先认识 ROS 2：它不是算法，而是一套“机器人公司”协作规则

先别被 SLAM、DDS、TF2 吓到。ROS 2 不是操作系统，也不会自动让机器人变聪明；它是让多个程序按统一规则交换信息、一起启动和排错的机器人软件框架。

NODE = 员工

一个节点只做一类事

把机器人想成一家公司：激光驱动、相机驱动、定位、建图、导航都是不同员工。每个节点各司其职，通过统一接口协作，而不是把所有逻辑塞进一个大程序。

  • 例如 lidar_node 只发布扫描；slam_node 只消费数据并估计地图。
  • 好处是可单独启动、替换、记录和排错。
MESSAGE = 标准表单

Topic、Service、Action 怎么选？

Topic 像广播电台，持续播放数据；Service 像前台问答，一问一答；Action 像外卖订单，任务长、可取消、过程会汇报进度。

  • 激光和 IMU 用 Topic，不等“回复”。
  • 读取一次配置可用 Service；导航到目标点适合 Action。
TF2 = 坐标翻译字典

时间戳是“翻译生效时间”

同一个障碍物在雷达坐标、车体坐标和地图坐标中的数字不同。TF2 记录“如何翻译”；时间戳说明“这份翻译是哪个时刻的”。

  • TF 断了，RViz2 常表现为模型不见或跳动。
  • 时间不同步，会把正确数据放到错误位置。

第一个 30 分钟：先听见 ROS 2 在说话

下面不是 SLAM，只是验证环境、节点和 Topic 是否可用。终端是机器人软件的“控制台”；每个命令都在回答一个小问题。

# 1. 让当前终端认识 ROS 2 Jazzy
source /opt/ros/jazzy/setup.bash

# 2. 开一个终端，启动“说话者”节点
ros2 run demo_nodes_cpp talker

# 3. 另开终端，同样 source 后启动“听话者”
ros2 run demo_nodes_py listener

# 4. 看现在有哪些广播频道
ros2 topic list

你应该看懂什么？

  1. talker 是发布者节点，周期性生成字符串消息。
  2. listener 是订阅者节点，收到同名 Topic 后打印消息。
  3. ros2 topic list 让你确认频道是否真实存在，而不是只猜代码“应该发布了”。
  4. 以后排查机器人也是同一套路：节点在不在、Topic 有没发布、频率对不对、数据的 frame_id 与时间戳对不对。

补充 2 · 先看学习地图，再从第一步开始动手

不要按页数硬啃。先从 ROS 2 的命令与节点开始，沿着“能看见 → 能改动 → 能排错 → 能解释”向 SLAM 深入；每个阶段都有可验证的小成果。

学习原则：ROS 2 教程解决“工程怎么搭、消息怎么流”；图优化与状态估计资料解决“位置为什么会漂、怎样把它拉回来”。点击阶段，按“要懂什么 → 工作中做什么 → 得到什么”推进。

Step 01 / First contact

先听见两个节点在同一频道说话

一开始只确认三件事：终端已经 source ROS 2；节点可以运行；Topic 里真的有消息。把这三件事做通，比直接装 SLAM 包更重要。

  • 运行 talker 和 listener，观察一发一收。
  • 用 ros2 node list、ros2 topic list、ros2 topic echo 看事实。
  • 理解：程序叫节点，频道叫 Topic，消息是统一格式的表单。
本阶段可交付能用命令确认一个节点、一个 Topic 和一条消息工作中：遇到“没有数据”，先检查节点是否运行、Topic 是否存在、内容是否在更新。

补充 3 · ROS 2 概念速记：先记住画面，再回到工程事实

比喻是帮助理解的扶手，不是技术定义。点一个概念，先看它像什么，再看它在真实 ROS / SLAM 工程里要检查什么。

SOURCE

给终端发一张“园区通行证”

每开一个终端，source 就像给它发通行证：它这才知道 ROS 2 的命令和刚构建的程序分别在哪个“园区”。

工程事实：它会在当前 shell 设置环境变量；新开终端、构建工作空间后忘记 source，常会出现“找不到 ros2 / 找不到包”。

上手动作：命令找不到时，先检查当前终端是否 source 了 ROS 2 和工作空间的 setup.bash。

补充 5 · 给机器人数据补上空间与时间

数据能够传到不代表能用：坐标变换并非只有“从 A 到 B”，还需要知道它在什么时刻成立。时间不同步会让正确的几何关系在错误时刻被使用。

SENSOR FRAME激光、相机或 IMU 的安装坐标系。
BASE_LINK车体参考坐标，连接传感器外参。
ODOM局部连续但会累计漂移的里程计参考。
MAP全局地图参考，由定位/SLAM 修正。

补充 6 · 进入 SLAM 前，先分清各自职责

不要急着背算法名。先理解前端、后端、回环和建图分别解决什么问题；这一章看完，再进入下一章的图优化实验。

FRONTEND

匹配与里程计

利用激光、视觉、IMU 或轮速数据估计相邻时刻位姿。输出常会有累计误差，不能当作全局绝对真值。

  • 关注特征/扫描匹配和传感器时间。
  • 观察轨迹是否连续稳定。
BACKEND

图优化

将里程计、回环等约束放入图中优化全局位姿，目标是在多种观测之间取得整体一致性。

  • 异常约束会拉扯整条轨迹。
  • 优化频率与计算资源需要平衡。
LOOP / MAP

回环与地图

回环识别到曾经到过的位置后可提供闭环约束，抑制漂移；建图则输出栅格或点云等环境表示。

  • 错误回环可能导致地图折叠或跳变。
  • 使用现成包属于工程集成，不等于自研算法。

Chapter 09 / integration debug

补充 9 · 集成与调试路径

RViz2 中地图不更新或机器人位置跳变怎么办？

按传感器数据、时间戳、frame_id、TF 树连通性、里程计质量、SLAM 节点日志逐层检查。先用 rosbag2 固化可复现数据，再调参数。

Nav2 是否等于 SLAM？

不是。Nav2 主要处理导航行为与路径规划；SLAM 负责定位/建图。项目中可以把二者与已有定位或地图服务集成，但需说明各自职责。

Chapter 10 / interview drills

补充 10 · 用高频追问复盘关键概念

TF2 为什么需要时间戳？

查询的是某个时刻的坐标关系。时间不同步、发布频率不足或请求超出缓存会导致外推错误，从而让融合或定位使用错误变换。

QoS 为什么会让 Topic 看似“收不到消息”？

发布者和订阅者的可靠性、持久性等策略不兼容时可能无法匹配；还要检查命名空间、消息类型和实际发布频率。
