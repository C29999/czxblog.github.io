Module 02 / system coordination

从任务调度到系统边界

FreeRTOS 处理资源受限 MCU 上的任务协作；Linux 通过用户态、系统调用和驱动管理更完整的系统资源。面试重点是明确两者的边界与取舍。

任务与调度

先解释调度器选择谁运行，再讨论任务优先级、周期与实时性；不要将“高优先级”误解为永远占用 CPU。

同步与数据通信

Linux 系统边界

Linux 用户态程序不是直接操作硬件，而是通过库、系统调用、设备文件或专用框架进入内核驱动。

USER SPACE

进程与接口

应用负责业务、数据处理和错误处理；调用 open/read/write/ioctl 或系统库接口请求内核提供服务。

  • 查看返回值、errno 和超时策略。
  • 用日志定位应用层状态机。
KERNEL

驱动与总线

驱动对接 I²C、SPI、UART、GPIO 或网络控制器，并向用户态暴露设备节点、sysfs 或专用 API。

  • 理解设备树、驱动匹配与 probe。
  • 区分内核日志和用户态日志。
DEBUG

分层排错

从应用参数、系统调用、驱动日志到电气波形逐层缩小范围，避免一开始把问题归因于“驱动坏了”。

  • 先确认设备是否枚举和节点权限。
  • 再检查总线地址、时序与供电。

Linux TCP：从 socket 到 close

把 TCP 放进 Linux 的真实运行路径理解：应用只操作 fd；连接状态、可靠传输、重传、窗口和队列都在内核协议栈中完成。

面试先给结论：TCP 是面向连接、可靠、有序的字节流。它可靠地交付字节序列，但不保留业务消息边界，也不代表对端业务一定处理成功；长度、超时、重试和业务确认仍要由应用协议设计。

SOCKET LIFECYCLE

一个 fd，两类角色

socket() 创建内核 socket 对象并返回文件描述符。服务器用监听 fd 接受新连接；每次 accept() 返回独立的连接 fd，监听 fd 仍继续接客。

socketbindlistenaccept
  • 客户端路径：socket → connect → send/recv。
  • 服务端连接 fd 才用于实际收发。
  • 非阻塞 connect 返回 EINPROGRESS 后，需等可写并用 SO_ERROR 判定结果。
KERNEL BUFFERS

send 成功，代表什么？

通常只表示本次返回的字节已被本机内核接收进入发送路径；它既不等于数据已到达对端，也不等于对端应用已经处理。

SYN

1 / 10 · SYN：客户端调用 connect()，内核从本地发送 SYN；此时客户端通常处于 SYN_SENT，服务端仍在 LISTEN。

三次握手为什么是三次？

双方要确认两个方向都可收可发，并同步两边的初始序号：SYN 请求、SYN+ACK 确认并给出自己的序号、最后 ACK 完成确认。不是一句“为了防止旧连接”就能概括完。

四次挥手也不是绝对四包

关闭是两个方向分别终止：一方 FIN 后，对端仍可发送剩余数据，再发 FIN。ACK 与 FIN 在某些时机能合并，因此抓包中不一定恰好看到四个独立报文。

TIME_WAIT 不等于故障

主动关闭方常进入 TIME_WAIT，用于可靠重传最终 ACK，并让网络中的旧报文失效，避免干扰后续相同四元组的连接。排查时关注数量与端口耗尽，不要粗暴“清掉”。

epoll ET：一次可读，要读到 EAGAIN

ET（边缘触发）只在“不可读变为可读”时提醒。连接 fd 必须非阻塞；收到事件后循环读取，直到内核接收缓冲被读空。

/* fd 已用 accept4(..., SOCK_NONBLOCK) 接入，并注册 EPOLLIN | EPOLLET */
static int drain_rx(int fd)
{
    char chunk[4096];

    for (;;) {
        ssize_t n = recv(fd, chunk, sizeof chunk, 0);
        if (n > 0) {
            rx_append_and_parse_frames(fd, chunk, (size_t)n);
            /* 按长度字段/分隔符拆帧，缓存未解析残留字节 */
            continue;
        }
        if (n == 0) return 0;       /* 收到 FIN：读完缓存后的有序 EOF */
        if (errno == EINTR) continue;
        if (errno == EAGAIN || errno == EWOULDBLOCK) return 1;
        return -1;                  /* 其他错误：记录 errno 后关闭连接 */
    }
}

阻塞、非阻塞与背压

epoll 的事件是“现在值得继续尝试 I/O”的就绪通知，不是“一个完整协议包已到”或“本次肯定能读/写完”。

  1. 阻塞 recv 无数据时会等待；非阻塞 fd 无数据通常是 EAGAIN/EWOULDBLOCK。
  2. LT（默认）只要仍可读/写可持续通知；ET 必须尽力读/写到 EAGAIN。
  3. EPOLLONESHOT 触发后需用 EPOLL_CTL_MOD 显式 rearm，适合短暂交给一个工作线程。
  4. 写路径也会短写：保存未发完的数据，只在需要时监听 EPOLLOUT；不要无界堆积用户态队列。
  5. 处理 EPOLLERR、EPOLLHUP、EPOLLRDHUP；HUP 时可能还有最后一批可读字节，先 drain，再用 SO_ERROR 判断具体错误。

Interview drills

高频追问

队列、信号量和事件组各适合什么？

队列主要传数据；信号量侧重同步或资源计数；事件组表达多个独立标志位。回答要补充任务/ISR 使用限制和超时处理。

Linux 应用读设备文件失败，如何定位？

依次确认设备枚举、节点与权限、应用参数和返回值、内核日志、驱动状态，最后再检查硬件连接与总线波形。

recv() 返回 0、EAGAIN、EINTR 各说明什么？

返回 0 表示对端有序关闭，且已读完本地接收缓冲中的数据；非阻塞 fd 的 EAGAIN/EWOULDBLOCK 只是暂时无数据；EINTR 是系统调用被信号打断，通常按策略重试。只有其他错误才进一步按 errno 判断是否断连或异常。

close() 与 shutdown(SHUT_WR) 有什么区别？

close() 关闭本进程持有的这个 fd；当最后一个引用关闭时会进入 TCP 关闭过程。shutdown(SHUT_WR) 只关闭写方向，在已经排队的数据之后发送 FIN，应用仍可继续 recv() 对端剩余响应，适合“请求发完、继续等回应”的半关闭。

TCP 出现“粘包/拆包”怎么回答？

不要说 TCP 把包粘错了。TCP 只提供有序字节流，没有业务消息边界；一次 send 与一次 recv 不必一一对应。协议层要定义固定长度、分隔符（并处理转义）或长度字段 + payload，并在接收缓存里循环解析完整帧和校验长度。

为什么向已关闭连接写数据，进程可能被 SIGPIPE 终止？

对端已经关闭或复位时，send/write 可能返回 EPIPE；默认处理 SIGPIPE 会终止进程。网络服务通常使用 MSG_NOSIGNAL，或按进程策略忽略 SIGPIPE，并将 EPIPE 当作该连接的关闭信号进行清理。

Linux 上怎样分层定位连不上、卡住或频繁重传？

先用 ss -ltnp 看监听端口和进程，用 ss -tanpi 看连接状态、队列和 TCP 信息；再用 tcpdump -ni eth0 -nn 'tcp port 8080' -vv 看握手、重传、RST、FIN 与窗口；用 strace -ff -e trace=network -p <PID> 看 accept/connect/send/recv 与 errno。必要时补查 nstat、ip -s link、dmesg -T 和应用日志。
